Ein nacktes =podman-compose up= in diesem Verzeichnis startet die
Entwicklungsumgebung. Produktion erfordert die explizite Angabe von
=compose.prod.yaml=.

Wer länger auf der Produktion arbeitet, setzt die Dateiliste einmal pro
Sitzung, statt sie an jeden Befehl zu hängen:

#+begin_src bash

  export COMPOSE_FILE=compose.yaml:compose.prod.yaml
  podman-compose exec db psql -U mantis_user -d mantis_tracker

#+end_src

Ohne die Variable landet man in der Entwicklungsumgebung — das ist so
gewollt, Produktion muss man verlangen.

=just= deckt nur noch das ab, was eigene Logik hat: =prod-backup=,
=prod-deploy=, =prod-rollback= und =prod-down=. Alles andere ist ein
gewöhnlicher compose-Befehl.

** Logs: zwei Fallen

=podman-compose= schreibt Containerausgaben auf beide Ströme — den
gunicorn-Zugriffslog nach stdout, den Flask-Logger und Postgres nach
stderr. Ohne =2>&1= findet ein nachgeschaltetes =grep= nichts, obwohl die
Zeilen auf dem Bildschirm stehen (Issue #178):

#+begin_src bash

  podman-compose logs --tail 100 web 2>&1 | grep -i error

#+end_src

=-f= bedeutet vor dem Unterbefehl die Compose-Datei und danach
=--follow=. Also =podman-compose logs -f web=, nicht =podman-compose -f
logs web=.

Der Log eines Containers beginnt mit dem Container, und =prod-deploy=
erzeugt ihn neu — er reicht also nie über den letzten Deploy hinaus. Die
durchgehende Historie liegt in journald, lesbar nur von einem Konto mit
Journalzugriff:

#+begin_src bash

  sudo journalctl _UID=$(id -u mantis) --since '3 days ago'

#+end_src

* Arbeiten mit Podman/Podman-Compose
** Stoppen
*** Anhalten: Stoppen 
#+begin_src bash

  cd infrastructure
  # podman-compose down
  podman-compose down

  # if production

  podman-compose -f compose.yaml -f compose.prod.yaml down
  
#+end_src

*** Anhalten: Stoppen und Volumes löschen
Falls alles frisch aufzusetzen ist:

#+begin_src bash

  podman-compose down -v

#+end_src

(-v entfernt auch die Volumes, also deine PostgreSQL-Daten!)
** Löschen: Altes Image

#+begin_src bash
  
  podman images
  podman image rm <image_name_or_id>
    
#+end_src
** Löschen: <none> - Images
#+begin_src bash
  podman image ls -a | grep '<none>' | awk '{print $3}' | xargs podman rmi -f
#+end_src
** Löschen: Frontend-Build verwerfen

Der Vite-Service baut nach =app/static/build/=, einem Bind-Mount ins
Repo — es gibt kein Volume zu löschen.

#+begin_src bash

  rm -rf ../app/static/build
  podman-compose up

#+end_src

** Starten:
*** Podman-Compose -- development

#+begin_src bash
    # 1. Dependencies installieren (einmalig / CI)
    bun install

  # 2. Frontend im Watch-Mode (nur nötig, wenn ohne vite-Container gearbeitet wird)
    bun run watch
  
    # 3. Container starten
    cd infrastructure
    podman-compose up

#+end_src

*** Podman-Compose -- production

#+begin_src bash

  # 1. Fertige CSS bauen
  bun run build

  # 2. Docker Image bauen
  podman build -t mantis_web ..

  # 3. Container starten
  podman-compose -f compose.yaml -f compose.prod.yaml up -d
  podman-compose -f compose.yaml -f compose.prod.yaml up -d --build

#+end_src
